# 小知 × 拾光 AI 优化方案（提示词与技能）

> 版本：v1 草案 · 2026-11-28
> 范围：小知（Agent 系统提示词 / 技能体系 / 工具描述 / **输入提示词润色**）、拾光（**AI 润色技能与提示词**：日记生活化、感悟哲学化与文笔）
> 目标：用「提示词分层 + 技能渐进披露 + 输入/输出双向润色」提升可用性，同时保持现有架构（Cordis 插件、OpenAI 兼容 LLM）不变。

---

## 0. 结论先行（TL;DR）

| 方向 | 现在 | 改成 | 收益 |
|---|---|---|---|
| 小知提示词 | 1 段 ≈120 字默认 prompt | **分层结构（角色/职责/工具纪律/回答风格/边界/输出格式）+ 4 条 few-shot** | 工具调用更准、答案更稳、越权与幻觉更少 |
| 小知技能 | 只有 5 个工具，没有"技能"概念 | **Skill Registry（SKILL 式索引 + `use_skill` 按需加载）**，先落 4 个技能 | 长流程（整理/写作/调研）有稳定套路，主 prompt 不膨胀 |
| 小知输入 | 用户原话直传 | **「✨优化」按钮**：把含糊输入补全成「目标+受众+约束+输出形态」，确认后发送 | 少一轮澄清，命中率提升 |
| 拾光润色 | 1 段 ≈120 字 prompt，无风格选项 | **风格卡 + 强度档 + 段落级 + 双候选**，日记/感悟分开建模 | 日记更生活化、感悟更有哲思与文笔 |
| 评测 | 无 | 小知 24 条金标 + 拾光 20 篇 rubric，接入 CI 可选 | 改动可度量、可回滚 |

## 1. 现状诊断（基于代码事实）

### 小知
- 系统提示词：`packages/plugins/agent/src/index.ts:37`，默认仅一句："你是「小知」…优先调用 knowledge_search…写文档调用 knowledge_add / knowledge_update"。
- 工具：5 个（`knowledge_search`、`current_time`、`web_fetch`、`knowledge_add`、`knowledge_update`），描述 1 句话；写工具带 `requiresApproval`。
- 循环：`runStream()` 最多 `maxSteps=10` 轮，system + 历史 + 本轮消息；无「技能/流程」抽象，无输出格式约束。
- 观察到的风险：
  1. 没有「什么时候不要用工具」「工具失败后怎么办」的纪律 → 容易空转/重复检索；
  2. 没有回答格式约定 → 有时长篇大论、有时直接把检索原文倒出来；
  3. 写文档工具允许 `content` 整篇替换，缺「先展示 diff 再确认」的提示词约束（虽然有审批）；
  4. 用户输入短/含糊时（"整理一下"）没有补全机制。

### 拾光
- 润色接口：`packages/api/src/routes/shiguang.ts:157-204`，固定 prompt，`temperature 0.6`、`maxTokens 1600`、正文上限 4000 字，仅 diary/insight，返回单个结果。
- 前端：`ShiguangPanel.vue` 只有「AI 润色 → 采纳替换 / 放弃」，无风格、强度、段落选择、多候选。
- 问题：日记与感悟共用同一句"日记保持真实口语化；感悟保持凝练克制"，**没有细化的操作清单**（怎么算生活化？怎么算有哲思？），模型只能泛泛而谈，容易把日记润成作文、把感悟润成鸡汤。

---

## 2. 设计原则（参考成熟做法）

1. **提示词分层**：角色 → 任务 → 约束 → 输出格式 → 示例，用 XML/标签分区，便于模型定位与后续局部改版（参考 Anthropic 提示词结构实践 [^1]）。
2. **技能渐进披露**：主提示只放「技能名 + 何时用」，正文按需加载（`use_skill` 读取），保持主上下文精简（Anthropic Agent Skills 的核心设计 [^2][^3]）。
3. **工具描述写"何时用/何时不用"**：3–5 句 + 反例，比一句"检索知识库"更有效（函数调用指南建议显式声明工具边界 [^4][^5]）。
4. **输入侧润色（prompt rewriting）**：把用户口语改写成结构化指令，已被证明能显著提升下游任务表现（TAPR 等工作 [^6]）；产品化时需**让用户确认**，避免"替用户改意思"。
5. **输出侧润色**：风格规范必须写成**可检查的清单**（动词化的编辑动作），而不是形容词堆叠。
6. **一切可回归**：prompt 带版本号、有金标集、可灰度、可一键回滚。

## 3. 小知优化方案

### 3.1 系统提示词 v2（替换 `Config.systemPrompt` 默认值）

```text
<role>
你是「小知」（DocCurator），i-kit 知识库的文档管理员与写作搭档。你熟悉站主的文档习惯：中文、简洁、重结构、少套话。
</role>

<responsibilities>
1) 检索与答疑：先查库再回答；库里有就引用，没有就明说。
2) 整理与归类：合并重复、拆分长文、补标签与上级文档。
3) 写作与改写：新建/续写/改写在库文档（需审批）。
4) 站务协助：解释功能、给操作路径，不臆测系统行为。
</responsibilities>

<tool_discipline>
- knowledge_search：问题涉及"站内资料/我之前写过/文档里有没有"时**必须**先检索；闲聊、常识、计算不必检索。
- 检索一次不够时，换关键词最多再试 1 次；仍无结果就回答"知识库中没有相关内容"，并给出可以怎么补。
- web_fetch：仅当用户明确要求"查网上/最新"时使用；一次对话最多抓 2 个链接。
- knowledge_add / knowledge_update：写入前先用一句话说明将改什么；不确定目标文档时先 knowledge_search 确认，不要凭标题猜。
- 工具报错：把错误翻译成用户能理解的一句话，并给出下一步（换关键词/补标题/稍后重试），不要原样抛栈。
</tool_discipline>

<answer_style>
- 默认中文；先给结论，再给依据/步骤；能用 3 句说清就不写 10 句。
- 引用知识库时标注来源，如「参考《Cordis 插件框架》」。
- 列表 ≤7 条；代码/命令用代码块；不输出 emoji（除非用户用了）。
- 不确定就说不确定，并说明缺什么信息。
</answer_style>

<boundaries>
- 不编造文档内容、不虚构引用、不替用户做未经确认的发布/删除。
- 涉及权限（草稿、私密、用户组）时按调用者可见性说话，不暗示他人文档存在。
- 不输出与任务无关的长篇背景。
</boundaries>
```

配套 4 条 few-shot（放在 `Config.promptExamples`，或直接拼在 system 末尾）：
1. 站内检索类（含"库里没有"的兜底）；
2. 整理类（先列合并方案再执行）；
3. 写作类（先给提纲，确认后 knowledge_add）；
4. 越权/未知类（拒绝并给替代路径）。

### 3.2 技能体系（Skill Registry + 渐进披露）

**为什么不是"再加工具"**：工具是"能力"，技能是"流程知识"。当前 5 个工具足够，缺的是"整理文档的套路""写作规范"这类长文本流程，塞进主 prompt 会膨胀，正好用 SKILL 模式。

**数据结构**（新增 `packages/plugins/agent/src/skills.ts`）：

```ts
export interface AgentSkill {
  name: string                 // 唯一 id，如 'knowledge_curator'
  title: string                // 中文名
  description: string          // 何时用（触发信号）+ 何时不用（边界），≤80 字
  body: string                 // 流程正文（≤1500 字），use_skill 时注入
  tools?: string[]             // 该技能推荐搭配的工具
  requiresAdmin?: boolean      // 写类技能
}
```

**注入方式**：
- 主 prompt 末尾追加「可用技能」索引（只有 name + title + description）；
- 新增工具 `use_skill(name)`：返回该技能 `body`（一条 system 消息追加进对话），并提示"按此流程继续"；
- 技能正文只在被加载时进入上下文 → 主上下文稳定在 1–2k 字。

**首批 4 个技能**：

| 技能 | 触发 | 正文要点 |
|---|---|---|
| `knowledge_curator` 文档整理 | "整理/归档/分类/去重/合并" | ①先检索候选 ②列"保留/合并/拆分"方案 ③等确认 ④逐条执行并汇报 ⑤更新标签与上级 |
| `doc_writer` 文档写作 | "写一篇/续写/改成教程" | ①确认读者与目标 ②给提纲（3–6 节）③逐节写入 ④自查：标题层级/代码块/链接/长度 |
| `research_web` 联网调研 | "查一下最新/对比" | ①拆 2–3 个查询 ②web_fetch（≤2 链接）③列"来源 + 结论 + 不确定点" ④不把网页原文整段贴出 |
| `daily_assistant` 站务助手 | "怎么用/在哪设置" | 按「功能 → 入口 → 步骤 → 注意」回答；不确定的功能先 knowledge_search |

**实施要点**：
- 技能索引放 system，`use_skill` 结果以 `role: 'system'` 追加（或 tool 结果），并加一句"已加载技能：X"；
- 技能 body 带 `version` 字段，便于 A/B；
- 写类技能仍走 `requiresApproval`，审批卡展示「将执行技能 + 关键参数」。

### 3.3 工具描述规范化（逐个改写）

统一模板：**做什么 → 何时用 → 何时不用 → 失败怎么办**，3–5 句；参数补 `description` 与示例。

以 `knowledge_search` 为例：

```text
在站主的知识库中做语义/关键词混合检索，返回最相关的若干条目（标题 + 正文）。
何时用：用户问"文档里有没有…""我之前写过…"，或需要引用站内资料支撑回答时。
何时不用：纯常识、计算、闲聊；用户明确要求联网时改用 web_fetch。
失败：返回"知识库中没有找到相关内容"时，换更具体的关键词再试一次；仍失败就直说没有，并建议补录。
```

其余 4 个工具按同一模板重写；`knowledge_update` 增加强约束："**若用户没有给出完整新正文，优先 append 或局部字段修改，禁止整篇 replace**"（避免误覆盖）。

### 3.4 用户输入提示词润色（「✨优化」）

**产品形态**：
- 小知输入框右侧新增「✨ 优化」按钮（与发送并列）；
- 点击后调用轻量 LLM（temperature 0.2，maxTokens 400）把输入改写成结构化指令；
- 结果以**可编辑**卡片展示：`优化后提示词` + `补充了哪些信息`（3 条以内）+「用这个发送 / 改一改 / 取消」；
- 空输入或 <6 字才自动建议（首次可提示一次，不打扰）。

**API**（新增，登录可用）：`POST /api/agent/prompt-polish`
请求 `{ text: string, context?: { sessionTitle?: string }, mode?: 'polish' | 'expand' }`
响应 `{ prompt: string, added: string[], intent: 'ask' | 'search' | 'write' | 'organize' | 'other' }`

**提示词草稿**：

```text
你是「小知」的提示词优化器。把用户的口语化输入改写为一条清晰、可执行的指令，供另一个助手执行。

规则：
1. 保留用户原意与所有事实、数字、专有名词，不新增事实、不替用户做决定。
2. 补齐（仅在能从上下文合理推断时）：目标、对象/范围、受众、约束（长度/风格/格式）、期望输出。
3. 不要把简单问题复杂化：能一句说清就一句；用户输入已完整时，只做轻微润色。
4. 输出必须是严格 JSON：
{"prompt":"改写后的指令","added":["补充点1","补充点2"],"intent":"ask|search|write|organize|other"}
5. 不输出 JSON 以外的任何文字。

<用户输入>
{{text}}
</用户输入>
<会话上下文>
{{sessionTitle}}
</会话上下文>
```

**前端**：`App.vue` / `DocCuratorPanel.vue` 输入区；失败时原地提示"优化失败，可直接发送"，绝不阻断发送。

### 3.5 上下文与多轮

- 历史裁剪：保留最近 8 轮 + 首轮用户意图摘要（>8 轮时由小模型压缩成 120 字摘要，缓存到会话）；
- 检索结果注入为 `[1]《标题》\n正文`，并提示"引用时标注 [1]"，减少"张冠李戴"；
- 会话标题自动生成（首轮 15 字内），与现有会话管理对齐。

### 3.6 评测与灰度

- **金标集 24 条**（存 `docs/eval/agent-cases.json` 或 `packages/plugins/agent/test/`）：检索 6、整理 5、写作 5、边界/越权 4、多轮 4；
- 指标：工具调用正确率、首次回答可用率（人工 1–5 分）、平均轮次、越权/编造次数（应为 0）；
- 灰度：`AGENT_PROMPT_V2=1` 控制新 prompt；`use_skill` 独立开关；按用户 id 分桶 50% 一周；
- 回滚：prompt 常量化 + 版本号，环境变量切回旧版即可。

## 4. 拾光优化方案

### 4.1 两类文本的风格规范（可检查的编辑动作）

**日记（更贴近生活）**——判定标准从"写成什么样"倒推：
1. **场景落地**：保留/补一个具体时刻或地点（"下午三点""楼下便利店"），不编造未提及的地名；
2. **感官细节**：至少 1 处可感知细节（温度、声音、气味、光线、手上的动作）；
3. **口语与短句**：允许"就…""挺…""有点…"，句子平均 ≤25 字；
4. **情绪曲线**：保留原来的情绪起伏，不硬拗正能量结尾；
5. **去作文腔**：删"通过这件事我明白了""总而言之"等总结句式；不强行升华。

**感悟（更富哲学与文笔）**：
1. **概念提炼**：从具体经历抽出 1 个可命名的概念（如"延迟满足""边界感"），并解释为什么；
2. **因果/张力**：写出一组对立或转折（"越…反而越…"），避免单线陈述；
3. **隐喻克制**：最多 1 个贯穿隐喻，不用网络热梗；
4. **文笔**：长短句交替，删形容词堆砌；引用最多 1 句且不编造出处；
5. **留白**：结尾不下结论，留一个开放问题或画面；
6. **长度**：原文 ±30%，不注水。

### 4.2 润色提示词 v2（替换 `shiguang.ts` 内联 prompt）

拆成「角色 + 风格卡 + 编辑动作 + 约束 + 自检 + 输出」，`system` 按类型注入：

```text
你是中文私人写作编辑，服务一位写日记与感悟的普通作者。你的工作是"编辑"，不是"代笔"。

<硬约束>
- 不改变原意与事实：人物、时间、地点、数字、引用一律不动；原文没有的信息不新增（可抽象，不可编造）。
- 保留第一人称与作者口吻；不把作者改造成别人。
- 只输出正文，不要解释、标题、引号、Markdown 代码块。
</硬约束>

<style_card>
类型：{{kind}}   // 日记 / 感悟
强度：{{intensity}}  // 轻 / 标准 / 深
{{style_rules}}   // 注入 4.1 对应清单
</style_card>

<editing_actions>
按顺序执行，但只做必要的：
1) 修错别字与语病；
2) 调整语序与断句，删重复与口水词；
3) 补足清单里缺失的 1–2 个细节/层次（不虚构）；
4) 控制篇幅在原文 ±{{lengthTolerance}}；
5) 通读，确保结尾不像模板。
</editing_actions>

<self_check>
输出前逐条确认：事实未变？口吻仍是作者？清单至少 2 条命中？没有新增专有名词？没有总结式套话？
</self_check>
```

调用参数建议：
| 类型 | intensity | temperature | maxTokens |
|---|---|---|---|
| 日记 | 轻 | 0.55 | 1200 |
| 日记 | 标准 | 0.65 | 1600 |
| 感悟 | 标准 | 0.6 | 1400 |
| 感悟 | 深 | 0.7 | 1800 |

### 4.3 技能化（交互与 API 扩展）

**API 扩展**（`POST /api/shiguang/polish`，向后兼容）：

```jsonc
// 请求（新增字段全可选）
{ "type": "diary|insight", "content": "...", "intensity": "light|standard|deep",
  "style": "plain|literary", "mode": "polish|expand|tighten",
  "range": { "start": 0, "end": 200 } }   // 段落级润色
// 响应
{ "text": "...", "alternatives": ["..."], "notes": ["补了1处感官细节", "删了2处总结句"] }
```

**四个「技能」**：
1. **细化（默认）**：按 4.1 清单补细节/层次；
2. **扩写**：原文 1.5–2 倍，补场景与心理，仍不虚构事实；
3. **收紧**：压到原文 60%–80%，删套话与重复；
4. **段落级**：只改选中段，上下文作为参考（避免全篇重写导致口吻漂移）。

**多候选**：并行 2 个（标准 + 深一档），前端左右对比，选一个采纳；成本高时仅对"感悟"开。

### 4.4 安全与事实保持

- 数字/日期/人名/地名做**逐字校验**：润色后比对，若原文出现的专有名词消失 → 标黄提示（前端）；
- 检测"新增专有名词"：输出中新出现的大写/书名号/引号内容，非原文则高亮；
- 敏感信息（手机号/身份证/地址）默认不参与润色替换，原样保留；
- 服务端记录 `promptVersion` + `model`，便于回溯。

### 4.5 评测

- **人工 rubric（5 维 × 5 分）**：原意保持、生活感/哲思、文笔、篇幅控制、口吻一致；
- 20 篇样本（10 日记 / 10 感悟，含 2 篇"纯事实记录"作反例）；
- 自动指标：长度变化率、专有名词保留率、套话词表命中数（"总而言之/通过这件事/让我明白"）、句均长；
- 上线门槛：rubric 平均 ≥4.0 且"专有名词保留率 = 100%"。

### 4.6 前端交互建议（`ShiguangPanel.vue`）

- 润色按钮旁加「强度」小下拉（轻/标准/深）与「风格」开关（朴素/文艺）；
- 结果卡：显示 `notes`（改了什么）+ 「并排对比」+「采纳 / 再来一版 / 放弃」；
- 编辑器中选中文字时，按钮变为「润色选中段」；
- 失败不阻塞保存，仅提示。

## 5. 共用基础设施

| 项 | 建议 |
|---|---|
| 模型选择 | 小知主对话沿用当前默认模型；输入润色/标题/摘要用**同一模型但低 maxTokens**，后续可切小模型降本 |
| 参数 | 小知回答 `temperature 0.3`；输入润色 `0.2`；拾光按 4.2 表 |
| 超时/重试 | 润色 20s 超时；失败最多重试 1 次（仅网络类错误） |
| 成本 | 技能正文按需加载、历史裁剪、输入润色仅按钮触发 → 预估 token 增量 <15% |
| 审计 | 复用现有 `audit`：新增 `agent.skill_load`、`agent.prompt_polish`、`shiguang.polish`（记录类型/强度/版本，不记正文） |
| 开关 | `AGENT_PROMPT_V2`、`AGENT_SKILLS`、`AGENT_PROMPT_POLISH`、`SHIGUANG_POLISH_V2` 四个 env，默认关→灰度开 |

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 新 prompt 让回答变长/变啰嗦 | few-shot 限制 + 评测"平均字数"指标；超阈值回滚 |
| 技能正文注入过多挤占上下文 | body ≤1500 字；同一会话最多加载 2 个技能 |
| 输入润色"替用户改意思" | 强制"只补不删"、可编辑确认、原文始终可见 |
| 拾光润色事实漂移 | 专有名词校验 + rubric 门槛 + 单候选先上线 |
| 成本上升 | 低 maxTokens、按需加载、灰度对比 token |

回滚：所有 prompt 走常量/配置 + env 开关；`git revert` 对应提交即可，无数据迁移。
