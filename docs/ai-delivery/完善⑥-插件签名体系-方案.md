## 1. 目标与非目标

### 1.1 目标

1. **防源头投毒**：在 ⑤ 的「内容哈希（防传输篡改）」之上，用单一官方 ed25519 密钥对**文件树规范序哈希**签名，客户端验签，把信任根从「registry.json 托管方可信」提升到「持有官方私钥者可签」。
2. **零新依赖、零语义漂移**：只用 Node 内置 `node:crypto`（ed25519）与已有 `adm-zip`；签名对象严格等于 P1 已实施的 `sha256OfFileTree` 结果，不改该函数。
3. **可用的工具链**：管理员/发布者能用两条命令完成「生成密钥」「签名发包」，并拿到可直接粘贴进 `registry.json` 的条目片段。
4. **分阶段不打断现状**：默认 `warn` —— 未签名包照常安装、仅在商店/管理页标灰、日志留痕；`enforce` 才拒装。切回 `off` 即完全等价于现状。
5. **状态可见**：商店列表与详情、安装/导入结果都给出「未签名 / 已签名（装机时验证）/ 验证通过 / 验签失败（含密钥未受信）」四类人类可读状态。

### 1.2 非目标（本期不做）

- **不自建服务端市场**（决策 5）：不改 `refreshRegistry`、不加 registry API、不做审核流/云端评分。
- **不做沙箱**（决策 6）：`node:vm`/worker/进程边界另立项；本方案不改变「第三方 `entry` 与主进程同权限」的既有事实，UI 风险提示继续保留（`PluginStore.vue:124`）。
- **不做 `versions[]` 多版本清单**：现状 registry 条目为单版本（`types.ts:66-78`），签名随单版本走；多版本清单另立项。
- **不做在线吊销列表（CRL）/透明日志（Sigstore 类）/时间戳服务**：吊销 = 从信任表移除该 `keyId`（§4.1.4）。
- **不做启动时全量重验已装包**：装机时验签结论落库后不再重算（避免每次启动哈希所有包）；如需，另立「管理端一键审计」项。
- **不允许插件自证**：`plugin.json` 与 loader 上报**不得**携带签名字段（与 ⑤ §4.1「不允许插件自报扫描结果」同源）。
- **不做前端 zip 解析**：不在浏览器里解析 zip comment 预览签名（避免引入前端 zip 库），导入前的签名状况由服务端返回结果告知。

### 2.2 本次分析新发现（决定改法）

**F1（高，必须修）：loader 会用插件包「自报」的 sha256 覆盖服务端计算值。**

`index.ts:81` 把 `manifest.sha256`（来自包内 `plugin.json`，由 `loader.ts:72` 原样读取）传给 `registry.upsertPackage`；`service.ts:281` 执行 `if (p.sha256) existing.sha256 = p.sha256`。而 `loader.loadAll()` 在每次启动都会跑（`index.ts:93`）→ **一个包只要在 `plugin.json` 里写个假 `sha256`，就能在每次重启后覆盖服务端安装时计算的真值**。后果：⑤ 的「远端缺 sha256 拒装」与 ⑥ 的验签结论都可被包自身伪造，`plugins.json` 里的哈希也不可信。

- 处置（1 行，建议与 ⑥ 同批）：`index.ts:70-82` **不再传递 `sha256`**（也不传任何签名字段）。字段本身可留在 `PluginPackageManifest`（`loader.ts:26`）以免动 manifest 结构。
- 备注：`validateZipBuffer` 构造的 manifest（`packaging.ts:138-152`）本就不含 `sha256`，故删除该传参不影响安装路径。

**F2（中，建议同批 3 行）：registry 声明的 `version` 从未与包内 `manifest.version` 比对。**

`installRemote` 只校验名称（`service.ts:419-421`），不校验版本。攻击者/失误的 registry 可以把**旧的已签名包**（内容与哈希、签名全都合法）标注成新 `version`，客户端「更新」后实际停留在旧版（静默降级/回滚攻击），而 sha256 与签名**都无法发现**。签名把「包内 manifest 可信」这一点建立起来之后，补上 `registry.version === manifest.version` 即可闭环（§4.3.4）。

**F3（低，已确认可行）：`adm-zip@0.6.0` 支持 archive comment 读写。**

`addZipComment` / `getZipComment`（`node_modules/adm-zip/adm-zip.js:246-258`），写路径在 EOCD 中落盘（`zipFile.js:354-356`、`:432-434`）。实测：comment 写入后可完整读回，且**不产生任何 zip 条目**（见 §2.3 实测 4）→ 用它携带签名对 `sha256OfFileTree` 零影响。

## 3. 选型对比

### 3.1 签名算法与库

| 方案 | 结论 | 理由 |
|---|---|---|
| **Node 内置 `node:crypto`（ed25519）** | ✅ **推荐** | Node ≥16 原生支持，`sign(null, data, key)` / `verify(null, data, key, sig)`；零新依赖、零供应链风险；Node 24 实测通过（§2.3-2） |
| `@noble/ed25519` | ❌ 否决 | 唯一收益是「不依赖 Node 内置」（浏览器/边缘运行时）——本项目验签只发生在服务端（Node），收益为零，反而引入新依赖与版本维护面 |
| `tweetnacl` / `libsodium-wrappers` | ❌ 否决 | 同上，且体积大、API 更繁琐；Ed25519 detached signature 语义与内置 API 等价 |
| RSA-PSS / ECDSA | ❌ 否决 | 密钥更大、签名更长、验签更慢；ed25519 是「单一密钥 + 无参数选择」的最简安全选型（评估 §3.2 已定 ed25519） |

### 3.2 被签名字节（语义必须唯一确定）

| 方案 | 结论 | 理由 |
|---|---|---|
| **树哈希的 64 位小写 hex 字符串（UTF-8，64 字节）** | ✅ **推荐** | ① 可直接从 `registry.json` 的 `sha256` / `plugins.json` 的 `sha256` **复制粘贴**复现，无需 hex 解码；② 无大小写/编码歧义（规范为小写后比对）；③ 第三方用 `openssl pkeyutl -rawin` 亦可用（带 `-rawin` 时对等）；④ 确定性签名便于 CI 复现 |
| 32 字节原始 digest（`Buffer.from(hex,'hex')`） | ⚠️ 备选 | 少 32 字节（无实际意义），但复现需先解码 hex；一旦有人对 hex 字符串签名而校验方对 digest 验签，会得到「永远验不过」的静默错位。**推荐统一走 hex 字符串**（本方案 §4.2.2 二选一已定，实施时不得混用） |
| payload 加域分离前缀（`i-kit-plugin-v1\0` + hash） | ⚠️ v2 预留 | v1 **不加**（可复现性优先；本系统签名的载荷类型唯一，无跨协议混淆面）；用信封 `schema` 字段预留演进：将来若改载荷定义，必须 bump `schema` 并经历双接受期（§9 风险 R3） |
| payload 绑定 `name`+`version` | ❌ 不需要 | `name`/`version` 都在 `plugin.json` 内、已被树哈希绑定；registry 侧的版本谎报由 F2 的版本比对闭环，比塞进载荷更简单 |

### 3.3 导入包（zip）携带签名的载体

| 方案 | 结论 | 理由 |
|---|---|---|
| **zip archive comment（前缀 `ikit-plugin-signature:` + 单行 JSON）** | ✅ **推荐** | ① **零语义漂移**：comment 不是 zip 条目，`sha256OfFileTree(files)` 一字不改；② `adm-zip` 已支持读写（§2.3-4）；③ 前端无需改动（服务端读取）；④ 前缀标记使「第三方工具写入的普通 comment」被安全忽略，不误判为坏签名 |
| 树内 sidecar `PLUGIN.SIG.json`（并在树哈希中排除该文件） | ❌ 否决 | 会**修改 `sha256OfFileTree` 语义**（引入排除规则），与「与现已实施的 sha256 校验一致」的既定决策冲突，且使历史哈希的解释出现分支（风险 R3） |
| 仅 API 请求体携带（不入 zip） | ⚠️ 作为**补充** | 保留（`{data, sha256?, signature?, keyId?, signedHash?, signedAt?}`），用于手工/CI 场景；但不能作为唯一载体，否则「导出→导入闭环」与离线分发丢签名 |
| 树内 `plugin.json.signature` | ❌ 否决 | 自引用悖论：`plugin.json` 是被哈希内容的一部分，无法在自身内部携带对自己树的哈希/签名；且违反「不允许插件自证」原则 |

### 3.4 验签时机

| 方案 | 结论 | 理由 |
|---|---|---|
| **落盘前验签（与 ⑤ 的 sha256 前置校验同点，先 hash→再验签→再落盘）** | ✅ **推荐** | `installFilesAtomically`（`service.ts:311`）是唯一落盘点，前置可保证 enforce 失败时**零副作用**（无 staging、无目标目录、无 `plugins.json` 变更） |
| 落盘后、`loadOne` 前验签 | ❌ 否决 | 已有磁盘写入，失败需回滚；且与 ⑤ 的「校验链全在落盘前」结构不一致 |
| 加载时（每次 `loadOne`/启动）验签 | ❌ 否决 | 启动抖动 + CPU 浪费；且「已装包」的信任决策已在安装时作出（见 §7.5 存储语义） |

## 4. 设计详述

### 4.1 密钥与工具链

#### 4.1.1 `scripts/gen-plugin-key.mjs`（新增，~90 行）

| 项 | 设计 |
|---|---|
| 用法 | `node scripts/gen-plugin-key.mjs [--out .keys] [--force] [--name official]` |
| 输出 | `.keys/plugin-signing.key.pem`（PKCS8，`mode 0o600`，`flag:'wx'` —— 已存在即报错，除非 `--force`）、`.keys/plugin-signing.pub.pem`（SPKI） |
| 打印（stdout，**绝不含私钥**） | ① `keyId`（派生值）；② 私钥文件路径与「**请立即离线备份、勿提交**」提示；③ 可直接粘贴的 `.env` 行（见下）；④ 可粘贴进 `src/trusted-keys.ts` 的 TS 片段（`{ keyId: { publicKey: '<base64 SPKI>', status: 'active' } }`） |


#### 4.1.3 签名信封（单一结构，两处载体共用字段名）

```jsonc
{
  "schema": 1,                       // 信封/载荷定义版本（载荷变更必须 bump，见 §9-R3）
  "alg": "ed25519",                  // 仅允许 ed25519，其它值 → MALFORMED（不静默降级）
  "keyId": "ikit-e62c2f517b242c05",  // 必填；必须等于由 pubkey 派生（§4.4.3）
  "signedHash": "<64 位小写 hex>",   // 必填；= 被签名载荷 = 树哈希
  "signature": "<base64url>",        // 必填；sign(signedHash 的 UTF-8 字节)
  "signedAt": "2026-10-01T00:00:00Z" // 可选、纯信息性（不参与验签、不参与信任决策）
}
```

- 出现在 **`registry.json` 条目**时：按 `signature/keyId/signedHash/signedAt` **平铺**（与既有平铺 `sha256` 一致，`sanitizeRemoteRegistry` 无需嵌套解析）；`schema/alg` 可省（缺省即 `1`/`ed25519`）。
- 出现在 **zip comment** 时：`ikit-plugin-signature:` + 上述 JSON 单行（含 `schema/alg`）。
- 出现在 **API 请求体**时：与 registry 条目同形的平铺字段（覆盖 zip 内信封；两者都存在时以请求体为准并记 warn 日志）。

#### 4.1.4 `keyId` 与密钥轮换 / 吊销

| 项 | 设计 |
|---|---|
| `keyId` 生成 | `'ikit-' + sha256(SPKI-DER).slice(0,16)` —— **由公钥派生**，不可人为指定，杜绝「标签与密钥错位」 |
| 启动校验 | 信任表里每个 `keyId` 都重算派生值比对；不一致 → 启动 `console.warn` 并**忽略该项**（fail-closed，不会误信） |
| 轮换（加新密钥） | ① `gen-plugin-key.mjs` 生成新密钥 → 新 `keyId`；② 把新公钥**追加**进信任表（内置常量随版本发布，或该实例的 `PLUGIN_SIGNING_KEYS`）；③ 新包用新密钥签名；④ 旧 `keyId` 置 `status:'retired'` 保留在表中 → 旧包**仍验签通过**但记 `signatureWarning: 签名密钥已轮换（retired）` |
| 吊销（key 泄露） | 从信任表**删除**该 `keyId` → 其签名一律 `unknown-key`；enforce 模式下这些包无法新装/更新（已装的不受影响，符合 §7.5） |
| 单密钥起步 | 内置表默认**空**（见 §4.4.1）；官方首个密钥发布时才写入内置表；`status` 字段从第一天就存在 → 轮换不需要改结构（决策 2 的「为轮换留字段」） |

### 4.2 签名格式与载体

#### 4.2.1 字段与编码（明确定义，无歧义）

| 字段 | 编码/约束 | 说明 |
|---|---|---|
| `sha256` | `^[0-9a-f]{64}$`（小写；⑤ 的 `isSha256Hex` 复用） | ⑤ 的完整性校验值 = 树哈希 |
| `signedHash` | 同上（必须存在） | **被签名载荷的显式副本**；必须等于本地计算的树哈希，否则 `PLUGIN_SIGNATURE_INVALID` |
| `signature` | base64url（`^[A-Za-z0-9_-]{86}$`；解码后 64 字节） | ed25519 detached signature |
| `keyId` | `^[a-z0-9][a-z0-9._-]{2,63}$` | 信任表键；派生值（§4.1.4） |
| `alg` | 枚举 `'ed25519'` | 其它值 → `PLUGIN_SIGNATURE_MALFORMED` |
| `schema` | 整数，当前 `1` | 载荷/信封定义版本 |
| `signedAt` | ISO 8601 字符串（信息性） | 仅展示；**不参与**任何信任判断 |

#### 4.2.2 被签名字节定义（唯一、可独立复现）

```
payload    := ASCII/UTF-8 编码的 <signedHash> 字符串（64 个小写 hex 字符，64 字节）
signedHash := sha256OfFileTree(files) 的小写 hex（files = 解压后的全部条目，含 plugin.json）
signature  := ed25519_sign(privateKey, payload)          // node:crypto: sign(null, payload, key)
VERIFY     := signedHash === sha256OfFileTree(解压文件)
              && crypto.verify(null, Buffer.from(signedHash,'utf8'), trustedKeys[keyId], signature)
```

**独立复现（第三方/CI）**：

```bash
# 1) 复算树哈希（从已导出的 zip，等价于服务端 sha256OfFileTree）
node scripts/sign-plugin.mjs --zip hello-signed.zip --print-hash
# 2) 只用公钥验签（无需私钥）
node scripts/sign-plugin.mjs --verify hello-signed.zip --pub .keys/plugin-signing.pub.pem
```

**纯 Node 内置 crypto 的等价实现**（把上面两步合成一段，用于交叉验证「脚本本身没写错」；`payload` 就是 `signedHash` 的 UTF-8 字节）：

```js
// 运行：node --input-type=module -e "<本段内容>"（工作目录 = 仓库根；adm-zip 仓库已有）
import AdmZip from 'adm-zip'
import { createHash, createPublicKey, verify } from 'node:crypto'
import { readFileSync } from 'node:fs'

const zip = new AdmZip(readFileSync('hello-signed.zip'))
const files = zip.getEntries().filter((e) => !e.isDirectory)
  .map((e) => ({ relPath: e.entryName, data: e.getData() }))
const h = createHash('sha256')
for (const f of [...files].sort((a, b) => (a.relPath < b.relPath ? -1 : a.relPath > b.relPath ? 1 : 0))) {
  h.update(f.relPath); h.update('\0'); h.update(f.data)
}
const treeSha256 = h.digest('hex')                                   // ① 树哈希
const env = JSON.parse(zip.getZipComment().replace(/^ikit-plugin-signature:/, ''))
const ok = env.signedHash === treeSha256 && verify(                  // ② 两步校验
  null,
  Buffer.from(env.signedHash, 'utf8'),
  createPublicKey(readFileSync('.keys/plugin-signing.pub.pem')),
  Buffer.from(env.signature, 'base64url'),
)
console.log(treeSha256, env.keyId, ok)                               // ok === true
```

> 实施时以 `scripts/sign-plugin.mjs --verify` 为唯一入口（脚本已把 comment 解析 + 树哈希复算 + 验签合成一条命令）；上面这段等价实现只用于交叉验证脚本实现是否正确，避免文档与实现各说各话。

- **不使用** `signedHash` 的 hex 解码字节；**不使用** zip 原始字节；**不加**任何前缀/后缀/换行（`signedAt`、`keyId`、`name`、`version` 均不在载荷内，理由见 §3.2）。

#### 4.2.3 三处载体与流转

```
打包/发布侧                    registry.json            客户端安装侧
plugins/hello ──sign-plugin──▶ sha256/signedHash/  ──▶ installRemote: 下载 → validateZipBuffer
   │                            signature/keyId/           → ① sha256 比对（⑤）
   └──(可选) --out signed.zip ──▶ signedAt                 → ② 验签（⑥，本方案的树哈希）
        zip comment = 信封                                   → ③ installFilesAtomically 落盘
              │                                                  → upsertPackage 记录签名状态
              ├── 前端导入：POST /api/plugin-store/import {data}   （服务端读 comment）
              └── GET /api/plugin-store/:name/export 重导出：把 plugins.json 里保存的
                  signature/keyId/signedAt 重新写回 zip comment（「导出→导入」闭环不丢签名）
```

| 载体 | 字段 | 备注 |
|---|---|---|
| `registry.json` 条目 | `signature`/`keyId`/`signedHash`/`signedAt`（平铺） | `sanitizeRemoteRegistry` 透传（缺则 `undefined`，不丢弃条目——⑤ 已确立「不丢弃以便管理员看到原因」） |
| zip archive comment | `ikit-plugin-signature:` + 信封 JSON（单行 ASCII） | 前缀不匹配 → **视为无签名**（避免误判普通 comment）；前缀匹配但 JSON 非法/字段缺失 → `PLUGIN_SIGNATURE_MALFORMED` |
| API 请求体 | `signature?`/`keyId?`/`signedHash?`/`signedAt?` | 优先级高于 zip comment；两者皆有且不一致 → 以请求体为准 + 记 warn |
| `plugins.json` 记录 | `signature`（原始 base64url）+ `signerKeyId` + `signedAt`（+ 验签状态字段） | 仅用于「导出保留签名」与审计，**不参与**后续验签（每次安装都重算） |

#### 4.2.4 为什么不动 `sha256OfFileTree`（语义冻结）

- ⑤ 的哈希比对与 P1 已发布包的 `plugins.json.sha256` 都建立在该函数现行语义上；任何「排除某文件」的改动都会让**历史哈希的解释出现分支**（旧包是否含被排除文件？），并使「用签名工具复现服务器哈希」不再显然成立。
- 因此 ⑥ **不改** `utils.ts:30-39`；签名信封走 zip comment（§3.3），导出时由 `exportPackageToZip` 附加 comment（同样是「不是条目」的方式）。
- 该冻结写入文档与脚本注释，并作为 §9-R3 的缓解措施与 AC-1 的断言点。

### 4.3 验签点与语义

#### 4.3.1 验签矩阵（按来源 × 模式）

| 来源 | 是否验签 | 无签名时 | 验签失败时 | 状态落库 |
|---|---|---|---|---|
| `catalog`（内置 7 条「假安装」） | ❌ 不入链路 | 照常安装（`service.ts:548-569`） | — | `signatureStatus: undefined`（前端不显示徽标） |
| `builtin`（`agent`） | ❌ 不入链路 | — | — | `undefined` |
| `remote`（registry 条目 / 显式 `packageUrl` / `update`） | ✅ **落盘前** | `off/warn`：装 + `unsigned` + warn 日志；`enforce`：**拒装 400** `PLUGIN_SIGNATURE_REQUIRED` | `off`：不验；`warn`：装 + `invalid`/`unknown-key` + 红标；`enforce`：**拒装 400** | 写 `signatureStatus/signerKeyId/signatureVerifiedAt/signatureError/signedAt` |
| `local`（`POST /import`） | ✅ **落盘前**（信封来自 zip comment 或请求体） | 同上（`enforce` 亦拒装——签名策略与来源无关；理由见 §10-Q5） | 同上 | 同上 |
| loader 启动上报（已在盘上的包） | ❌ 不重验 | 保留库中已有状态；库中无状态 → `unsigned`（灰标「未签名/安装于本功能上线前」） | — | **不写签名字段**（沿用「undefined 不清空」） |

#### 4.3.2 验签顺序（严格串行，先 hash 后签）

```
1) decodeZipBase64 → validateZipBuffer            → { manifest, files, treeSha256, envelope?, envelopeError? }
2) 名称比对（既有 service.ts:419-421）
3) 版本比对（新增 F2：registry.version === manifest.version，仅 registry 来源）
4) sha256 比对（⑤）：assertSha256(entry.sha256, treeSha256)      → PLUGIN_SHA256_MISMATCH
5) 信封解析/格式校验                                              → PLUGIN_SIGNATURE_MALFORMED
6) keyId 查信任表                                                 → PLUGIN_SIGNATURE_KEY_UNKNOWN
7) signedHash === treeSha256（防「签名与哈希字段错位」）           → PLUGIN_SIGNATURE_INVALID
8) crypto.verify(...)                                            → PLUGIN_SIGNATURE_INVALID
9) installFilesAtomically（落盘）→ upsertPackage（落状态）
```

- `warn` 模式：第 5–8 步的失败**不抛错**，改为 `verdict = { status: 'invalid'|'unknown-key', error }` 后继续第 9 步，并 `console.warn` 一行结构化日志。
- `enforce` 模式：第 5–8 步失败抛 `PluginError(msg, code)` → 路由 400；**第 9 步未执行，磁盘零副作用**。
- `off` 模式：跳过 5–8 与所有签名字段写入（完全等价现状）。

#### 4.3.3 状态枚举与展示文案

```ts
export type PluginSignatureStatus = 'unsigned' | 'unverified' | 'verified' | 'invalid' | 'unknown-key'
// undefined = 不适用（catalog/builtin）或旧记录未评估
```

| 状态 | 含义 | 何时产生 | 前端文案/配色 |
|---|---|---|---|
| `verified` | 验签通过 | 安装/导入时第 8 步通过（含 `retired` 密钥，附 warning） | 「🔒 已签名·验证通过」绿色 |
| `unverified` | 已声明签名、本机尚未验证 | ① 未安装的 remote 条目（只有 registry 声明）；② `off` 模式下有签名的记录 | 「🔏 已签名·装机时验证」蓝色（灰蓝） |
| `unsigned` | 无签名 | 包/条目无签名字段；或旧第三方记录 | 「未签名」灰色 + 说明「无法确认来源」 |
| `invalid` | 验签失败 | 第 5 步（信封字段/格式非法）、第 7 步（`signedHash` 与内容不一致）、第 8 步（`crypto.verify` 失败） | 「⚠️ 验签失败」红色 + `signatureError` |
| `unknown-key` | 签名密钥不在信任表 | 第 6 步失败（含启用「空信任表豁免」时除外，见下） | 「⚠️ 签名密钥未受信任（keyId）」红色 |
| `undefined` | 不适用 | catalog 7 条、builtin、`off` 模式 | **不显示任何徽标**（不误伤内置目录） |

**空信任表豁免（避免新装即满屏红标）**：若信任表为空（未配置任何公钥）且 `mode !== 'off'`，则「有签名但无表可查」记为 `unverified`（而非 `unknown-key`），并在启动时 `console.warn` 一条「未配置任何签名公钥，签名一律无法验证」。信任表非空时，未知 keyId 一律 `unknown-key`（真实信号，不掩盖）。

#### 4.3.4 版本一致性校验（F2，建议同批）

- 在 `installRemote` 增加可选入参 `expectedVersion?: string`；`install`/`update` 的 **registry 来源**传 `remote.version`；显式 `{packageUrl}` 来源无期望版本 → 跳过（文档写明）。
- 不匹配 → `PluginError('目录条目声明的版本（2.0.0）与包内 plugin.json（1.0.0）不一致，已拒绝安装', PLUGIN_ERR.STORE_VERSION_MISMATCH)`，HTTP 400；**warn 与 enforce 行为一致**（这不是签名开关，而是完整性事实错误，与 ⑤ 的 sha256 不匹配同级）。
- 收益：堵住「用旧签名包冒充新版本」的静默降级；否则签名通过但用户装到旧代码。

### 4.4 公钥分发与配置

#### 4.4.1 来源与优先级

```
信任表 = BUILTIN_TRUSTED_KEYS（src/trusted-keys.ts 常量，默认空）
       ∪ PLUGIN_SIGNING_KEYS       （可选 JSON：{"<keyId>":"<base64 SPKI>"|{"publicKey":…,"status":"active|retired"}}）
       ∪ PLUGIN_SIGNING_PUBKEY_FILE（单个 PEM 文件，keyId 由公钥派生）
       ∪ PLUGIN_SIGNING_PUBKEY      （单个 PEM 单行或 base64 SPKI，keyId 由公钥派生）
冲突（同 keyId）时优先级：PLUGIN_SIGNING_KEYS > PUBKEY(_FILE) > BUILTIN
```

| 来源 | 用途 | 默认 |
|---|---|---|
| 内置常量 `src/trusted-keys.ts` | **官方发布构建**把官方公钥写进代码，用户零配置即可验官方包 | **空表**（官方密钥尚未生成，不能臆造；空表有 §4.3.3 豁免兜底） |
| `PLUGIN_SIGNING_PUBKEY_FILE=./.keys/plugin-signing.pub.pem` | 自建/本地签名调试（与 `gen-plugin-key.mjs` 输出天然配套） | 未设置 |
| `PLUGIN_SIGNING_PUBKEY=<PEM 单行或 base64 SPKI>` | 单密钥最小配置（Docker/K8s Secret 注入，无需挂文件） | 未设置 |
| `PLUGIN_SIGNING_KEYS={"ikit-…":"<base64 SPKI>"}` | 多密钥/轮换过渡期（同时信任新旧两把） | 未设置 |

- 公钥是**公开信息**，可随配置/镜像分发；`.keys/` 目录整体 gitignore 仅因为私钥在其中（简化运维，避免「哪个文件能提交」的判断失误）。
- PEM 解析容错：支持字面 `\n` 还原（env 单行）、支持 base64（DER/SPKI）与 PEM 两形态；**非法公钥 → 启动 warn 并忽略该项**（不崩溃、不静默全信任）。

#### 4.4.2 配置项（`.env` / 插件 Config）

| 键 | 值 | 默认 | 说明 |
|---|---|---|---|
| `PLUGIN_SIGNATURE_MODE` | `off` \| `warn` \| `enforce` | **`warn`** | 非法值 → 按 `warn` 处理并 warn 日志（不 crash） |
| `PLUGIN_SIGNING_PUBKEY` | PEM 单行 / base64 SPKI | 空 | 单密钥 |
| `PLUGIN_SIGNING_PUBKEY_FILE` | 文件路径 | 空 | 单密钥（文件形态） |
| `PLUGIN_SIGNING_KEYS` | JSON 映射（keyId → 公钥） | 空 | 多密钥/轮换 |

对应插件 `Config`（`index.ts:18-36`）新增 `signatureMode?: string`（`Schema.string().default('warn')`）与 `trustedKeys?: Record<string,string>`（可选，供 JSON 配置注入）；env 优先级高于 Config（沿用 `registryUrl`/`allowHttp` 的既有范式 `index.ts:43-46`）。

#### 4.4.3 派生 keyId 的强制校验

- 每个信任表条目的 `keyId` 必须等于 `deriveKeyId(其公钥)`；不等 → 启动 `console.warn('[plugin-registry][signature] ignore key "<given>" (derived: <derived>)')` 并忽略。
- 目的：任何配置错位（贴错公钥、复制粘贴串行）都会在启动时暴露，而不会表现为「验签莫名失败」。

### 4.5 分阶段开关（warn → enforce）

#### 4.5.1 三模式行为矩阵

| 行为 | `off` | `warn`（默认） | `enforce` |
|---|---|---|---|
| 验签执行 | 否 | 是（如果包/条目带签名） | 是（必须带签名） |
| 无签名包安装（remote/import） | 允许 | **允许** + `unsigned` + 日志 warn | **拒绝** 400 `PLUGIN_SIGNATURE_REQUIRED` |
| 验签失败安装 | 不适用 | **允许** + `invalid`/`unknown-key` + 红标 + 日志 warn | **拒绝** 400 `PLUGIN_SIGNATURE_INVALID` / `..._KEY_UNKNOWN` |
| 落库签名字段 | 不写 | 写 | 写 |
| 商店 `installable/blockedReason` | 不受影响 | 不受影响（仅徽标） | 未签名/密钥未知/验签失败 → `installable:false` + 原因 |
| 前端按钮 | 常态 | 常态 + 灰/红徽标 + 安装前二次确认（风险文案） | 不可安装/更新（`disabled` + `title=blockedReason`） |
| 内置 7 条 catalog / builtin `agent` | — | — | **不受任何影响**（不入链路） |
| 已装包（含以前 warn 期装的未签名包） | — | — | 保持已装、可启停/卸载；**仅新装与更新被拦** |

#### 4.5.2 「何时可切 enforce」判据（建议写入发布检查表）

1. 官方 `registry.json` 中 **100%** 的条目都带 `signature/keyId/signedHash`（提供一条自查命令：拉 registry 后逐条 `sign-plugin.mjs --verify`）。
2. 官方公钥已进入**内置常量**（用户零配置可验），且至少经历 **1 个 release 周期**的 `warn` 运行。
3. 生产日志中 `[plugin-registry][signature] ... status=unsigned|invalid|unknown-key` **连续 30 天为 0**（或剩余命中均已被管理员确认为自建本地包）。
4. 运维文档（§11）已发布：密钥备份位置、轮换步骤、丢失应急预案。
5. 自建/本地导入场景的管理员已知悉：enforce 后未签名包无法导入，需先自签或配置其公钥。

> 切换动作本身是**环境变量变更**（`PLUGIN_SIGNATURE_MODE=enforce`，无需发版）；把**代码默认值**改为 `enforce` 属于后续版本决策，必须在判据 1–5 全绿后再做，并在版本说明中公告。

#### 4.5.3 迁移步骤（逐阶段）

| 阶段 | 动作 | 兼容性 |
|---|---|---|
| A（本期交付） | 代码合入，默认 `warn`；无任何公钥 → 满表 `unsigned`/`unverified`，**安装行为与现状一致** | 完全兼容；旧记录无新字段 |
| B | 运行 `gen-plugin-key.mjs` 生成官方密钥；私钥离线备份 + CI Secret；公钥写入 `registry.json` 发布流程；本地实例配 `PLUGIN_SIGNING_PUBKEY_FILE` 或内置常量 | 未签名包仍可装（warn） |
| C | 观察 §4.5.2 判据 3 的日志计数；把自建实例逐个切 `enforce`（先测试环境、再生产） | 已装未签名包不受影响；新装需签名 |
| D | 判据 1–5 全绿后，新版本把默认值改为 `enforce`（并保留 `PLUGIN_SIGNATURE_MODE=warn` 作为显式降级开关） | 公告 + 版本说明 |

### 4.6 错误码与 HTTP 语义

在 ⑤ 的 `PLUGIN_ERR`（`src/errors.ts`）中新增：

| 码 | 触发 | HTTP | 文案（示例） |
|---|---|---|---|
| `PLUGIN_SIGNATURE_REQUIRED` | `enforce` 下无签名 | 400 | `当前策略要求插件签名（PLUGIN_SIGNATURE_MODE=enforce），该包未携带签名，已拒绝安装。请使用带签名的包或改用已受信任密钥签名后重试` |
| `PLUGIN_SIGNATURE_MALFORMED` | 信封字段缺失/格式非法（`signature` 非 base64url、长度≠86、`signedHash` 非 64 hex、`alg ≠ ed25519`、`schema ≠ 1`、comment 前缀匹配但 JSON 非法） | 400 | `签名格式非法（<具体>），已拒绝安装` |

## 8. 验收标准（可操作 AC）

> 前置：`develop`（⑤ 已合，⑥ 已合），`PLUGIN_DIR=./plugins`，admin 会话（`Authorization: Bearer <token>`），本机 `plugins/hello` 存在（`plugins/` 已被 gitignore，不入库）。示例哈希 `369a7953…` 来自当前本机 fixtures，**断言请以所测环境的实际值比对**，不要硬编码文档里的值。

### A. 密钥与工具链

1. **生成密钥**：`node scripts/gen-plugin-key.mjs` → 生成 `.keys/plugin-signing.key.pem`（含 `BEGIN PRIVATE KEY`）与 `.keys/plugin-signing.pub.pem`；stdout 含 `keyId`、`.env` 行、`trusted-keys.ts` 片段；stdout **不含** `BEGIN PRIVATE KEY`。
2. **私钥不入库**：`git check-ignore -v .keys/plugin-signing.key.pem` 命中 `.gitignore:.keys/`；`git status --porcelain` **不出现** `.keys/` 下任何文件；`git log --all -p | Select-String "plugin-signing.key.pem|BEGIN PRIVATE KEY"` 无命中。
3. **幂等/防覆盖**：再次执行 `gen-plugin-key.mjs` 报错（已存在），`--force` 才覆盖。

### B. 签名与哈希语义一致性（防漂移，核心）

4. **签名产物**：`node scripts/sign-plugin.mjs --dir plugins/hello --out tmp/hello-signed.zip --registry-entry` → 打印的 `sha256` 为 64 位小写 hex、`signature` 为 86 字符 base64url、`keyId` 与 AC-1 的 keyId 一致、`signedHash === sha256`；`tmp/hello-signed.zip` 的 comment 以 `ikit-plugin-signature:` 开头。
5. **哈希语义一致（钉死漂移）**：`node scripts/sign-plugin.mjs --zip tmp/hello-signed.zip --print-hash` 的输出 **等于** 导入该 zip 后 `data/plugins.json` 中该包的 `sha256`（也等于 `GET /api/plugin-store` 中该项的 `sha256`）。
6. **独立验签（无私钥）**：`node scripts/sign-plugin.mjs --verify tmp/hello-signed.zip --pub .keys/plugin-signing.pub.pem` → `verified`；把 zip 内 `index.ts` 改一个字节再打包（不带 comment）→ `unsigned`；用同一 comment + 篡改内容的 zip → `invalid`。

### C. warn 模式（默认）

7. **签名包验证通过（远端）**：把 `tmp/hello-signed.zip` 挂到任意静态源（本地可用 `PLUGIN_REGISTRY_ALLOW_HTTP=1` + `python -m http.server`），`registry.json` 填入 AC-4 的条目片段 → `POST /api/plugin-store/refresh` 200 → `GET /api/plugin-store` 该项 `signatureStatus:'unverified'`（未安装）；`POST /api/plugin-store/install {"name":"hello"}` 200，响应 `signature.status:'verified'`；随后 `GET /api/plugin-store` 该项 `installed:true`、`signatureStatus:'verified'`、`signerKeyId` 回显、`signatureVerifiedAt` 为 ISO 时间；`data/plugins.json` 该记录含 `signature`（base64url）。
8. **签名包验证通过（本地导入）**：`POST /api/plugin-store/import {data:"<base64 of signed zip>"}`（不带请求体签名字段，仅靠 zip comment）→ 200 + `signature.status:'verified'`。
9. **未签名包（warn）**：导入不带 comment 的 zip（或 `{"name":"hello"}` 指向未签名条目）→ **200 安装成功**，`signatureStatus:'unsigned'`，服务端出现 `[plugin-registry][signature] … status=unsigned` warn 日志；前端卡片/详情显示灰色「未签名」，按钮**可用**（安装前出现二次确认）。
10. **篡改（warn，标红但不拒装）**：保留原 `signature/keyId/signedHash`，把 `sha256` 改成篡改后内容的新哈希（绕过 ⑤ 的哈希比对）→ 安装 **200**，`signatureStatus:'invalid'` + `signatureError` 含「签名与内容不匹配」；前端红色「验签失败」；包已落盘可正常启用。
11. **未知密钥（warn）**：registry 条目用未配置的 `keyId`（如 `ikit-0000000000000000`）→ 200 + `signatureStatus:'unknown-key'`，日志含 `key=ikit-0000…`。
12. **格式非法（warn）**：`signature` 改为 `"abc"` / `signedHash` 改为非 64 hex / `alg:"rsa"` → 200 + `signatureStatus:'invalid'` + `signatureError` 指明具体字段（enforce 下同一输入返回 400 + `code:"PLUGIN_SIGNATURE_MALFORMED"`）。
13. **空信任表豁免**：清空所有公钥配置（不设 `PLUGIN_SIGNING_*` 且内置表为空）→ 带签名的条目/包状态为 `unverified`（**不是**红标 `unknown-key`），启动日志含「未配置任何签名公钥」。

### D. enforce 模式

14. **未签名拒装（远端）**：`PLUGIN_SIGNATURE_MODE=enforce` 重启 → `POST /install {"name":"<未签名条目>"}` → **400** + `code:"PLUGIN_SIGNATURE_REQUIRED"`，且**未发生下载**（服务端无 fetch 记录）；`plugins/` 下无 `.staging-*`/`.backup-*` 残留。
15. **未签名拒装（导入）**：`POST /import {data:"<无签名 zip>"}` → 400 + `PLUGIN_SIGNATURE_REQUIRED`；`plugins/<name>` 未创建/未改动。
16. **验签失败拒装**：篡改内容 + 保留旧签名 → 400 + `code:"PLUGIN_SIGNATURE_INVALID"`；磁盘零副作用。
17. **未知密钥拒装**：400 + `PLUGIN_SIGNATURE_KEY_UNKNOWN`，错误文案列出当前信任表的 keyId。
18. **签名包正常安装**：同一 enforce 实例下 `POST /install {name:"hello"}` 200 + `signature.status:'verified'`；`GET /api/plugin-store` 该项 `installable !== false`。
19. **列表预标注**：enforce 下未签名/密钥未知的条目在 `GET /api/plugin-store` 中 `installable:false` + `blockedReason` 含「未签名」/「密钥未受信任」；前端安装/更新按钮 `disabled` 且 `title` 显示原因。
20. **版本一致性（F2）**：registry 条目 `version` 改为 `9.9.9`（包内 `1.0.0`）→ 400 + `code:"PLUGIN_STORE_VERSION_MISMATCH"`（warn 与 enforce 行为一致）；恢复正确版本后 200。

### E. 兼容与回归（不误伤）

21. **内置 7 条目录**：`GET /api/plugin-store` 中 catalog 条目**无**签名徽标字段（`signatureStatus === undefined`）；`POST /install {"name":"notes"}` 在 enforce 下仍 **200**（假安装路径不入验签链路）。
22. **builtin `agent`**：`GET /api/plugins` 中 `agent` 不受影响；启停/排序正常。
23. **旧数据兼容**：手工编辑 `data/plugins.json` 删掉某第三方记录的签名字段 → 启动/接口正常、前端不崩、徽标显示灰色「未签名」；开关 `PLUGIN_SIGNATURE_MODE=off` 重启 → 无新签名字段写入、无签名日志、无徽标（完全等价现状）。
24. **F1 回归（loader 不再自证 hash）**：构造 `plugins/fakehash/plugin.json` 内含 `"sha256":"0000…0000"` 的包 → 启动后 `GET /api/plugins` 中该记录 `sha256` **不等于**全 0（为空/或为服务端值），即自报值不再覆盖。
25. **导出→导入闭环（enforce）**：对 AC-18 安装的带签名 hello 执行 `GET /api/plugin-store/hello/export` → 导出 zip 的 comment 含 `ikit-plugin-signature:`；重新 `POST /import` **200 + verified**（签名随导出保留）。
26. **off 模式回落**：`PLUGIN_SIGNATURE_MODE=off` 下按 AC-9/10/11 重跑 → 全部 200 且**不写**签名字段（回滚路径有效）。

### F. 构建与安全

27. `pnpm -r --if-present build` **exit 0**（无签名字段类型错误；`PluginInstallResult`/`SignatureVerdict` 全链路通）。
28. **私钥不出现在任何日志/响应**：`Select-String -Path <server log> -Pattern "BEGIN PRIVATE KEY|PRIVATE KEY-----"` 无命中；`GET /api/plugin-store` 响应与 `data/plugins.json` 中无任何私钥材料（仅有公钥派生 `keyId` 与签名值 base64url）。
29. **`store()` 无重活**：`GET /api/plugin-store` 在 20+ 条目下响应时间与现状同量级（该路径不哈希、不验签、只查 keyId 表）。

## 9. 风险与回滚

| # | 风险 | 等级 | 说明 | 缓解 / 回滚 |
|---|---|---|---|---|
| R1 | **官方私钥泄露** | 高 | 攻击者可为自己签任意包；已发布包不受影响（仍指向旧 keyId） | 吊销 = 从信任表移除该 keyId（改配置/改内置常量 + 发版）；**换成新密钥重签已发布包**；`warn`→`enforce` 前置条件（§4.5.2）意在把窗口期风险降到最低；**私钥只存本地 `.keys/`（gitignored）+ 离线备份 + CI Secret，永不入库/入日志**（AC-2/28） |
| R2 | **私钥丢失** | 中 | 无法再签新包/新版本；已发布包仍可验证 | 生成新密钥（新 keyId）并加入信任表，旧 keyId 保留（`retired`）以维持旧包可安装；离线备份 + 备份位置记入运维文档（§11） |
| R3 | **签名与哈希语义漂移**（最高隐蔽风险） | 高 | 一旦 `sha256OfFileTree` 语义或载荷定义被改动，所有历史签名静默失效或出现「有的包过、有的不过」 | ① **本方案不动 `sha256OfFileTree`**（§4.2.4）并在该函数处加注释「语义已冻结，变更须 bump 信封 schema」；② 载荷定义固化在 §4.2.2 + AC-5 用「脚本 hash == 服务端记录 hash」钉死；③ 信封 `schema` 字段提供演进通道（改载荷必须 bump + 双接受期）；④ 签名脚本与 `utils.ts` 的 12 行重复实现由 AC-5 兜住漂移 |
| R4 | warn → enforce 兼容性 | 中 | 切 enforce 后，之前 warn 期安装的未签名包**留在盘上**（正是设计）；但用户可能误以为「切了就该拦住已装的」 | 文档/UI 明确「enforce 只拦新装与更新」；已装包仍可启停/卸载；如需清理，走「卸载 → 用签名包装回」；回滚 = `MODE=warn`（一条 env） |
| R5 | zip comment 被重打包工具丢弃 | 中 | 用普通工具解压再压缩会丢 comment → 变成未签名（enforce 拒装） | 现象确定（不会伪造出「验签通过」）；文档写明「分发用签名脚本产出的原始 zip」；API 请求体签名字段提供旁路；`--verify` 可在发布前自检 |
| R6 | registry 谎报版本（静默降级） | 中 | 旧签名包冒充新版本，哈希/签名都发现不了 | **F2 版本比对**（§4.3.4）——签名把包内 manifest 变成可信来源后才真正闭环；AC-20 |
| R7 | 验签进入热路径影响性能 | 低 | 每次安装多一次 `verify`（~50µs）+ 复用已有树哈希（无额外 IO） | `store()`/`list()`/启动**不做**加密运算（§4.3、AC-29）；`installFilesAtomically` 的哈希本就是既有开销 |
| R8 | 前端手写类型副本漂移 | 中 | `lib/plugins.ts` 是第二份定义 | §7.2 显式同步清单 + AC（grep `signatureStatus\|SignatureVerdict` 两端核对）+ `pnpm -r --if-present build` tsc 兜底 |
| R9 | 落地顺序冲突（⑤ 与 ⑥ 同改 5 个文件） | 中 | `service.ts`/`types.ts`/`routes.ts`/`lib/plugins.ts`/`PluginStore.vue` 双改 | **严格要求 ⑤ 先合、⑥ 基于 ⑤ 的提交做单提交增量**；不建议并行分支（合并冲突面大于收益）；⑥ 的所有改动都是「在 ⑤ 结构上加字段/加分支」 |
| R10 | 私钥被写进 `.env` 或截图外泄 | 低 | `.env` 已 gitignored 但仍可能被误发 | 推荐**不把私钥放 `.env`**（只放公钥相关配置）；私钥仅文件（`.keys/`）或 CI Secret；`gen-plugin-key.mjs` 打印的 `.env` 行只含公钥路径 |
| R11 | `signedAt` 被误当信任依据 | 低 | 签发时间由签名方自报 | 文档/UI 明确 `signedAt` 信息性、不参与验签；服务端权威时间放 `signatureVerifiedAt` |

**回滚总纲**

1. **配置级（秒级、无需发版）**：`PLUGIN_SIGNATURE_MODE=off` → 完全回到现状（不验签、不写字段、无徽标；旧值留在 `plugins.json` 里但被忽略，AC-26）。
2. **代码级**：⑥ 为单提交增量 → `git revert <⑥ 的提交>` 即回到 ⑤ 后状态；数据层只有可选键，**无需数据回滚脚本、无停机窗口**。
3. **密钥级**：密钥轮换/吊销见 §4.1.4，不影响已发布包的可验证性（除吊销目标密钥的包）。
4. 三项（⑤ 的 scan/sha256/拖拽）与 ⑥ **相互独立**，可分别回滚：⑥ 停用 = 不传 `signatureMode`（默认 warn 也只影响提示）或直接 `off`。
