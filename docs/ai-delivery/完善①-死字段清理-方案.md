## 4. SQLite 迁移方案

### 背景事实（影响方案的关键）

1. `SqliteStore.persist()`（`store.ts:154-208`）每次 `save()` 都执行 **`DELETE FROM entries`（及 categories/comments）+ 全量重新 `INSERT`**，即整表逐次重写。
2. 已部署服务器使用该库（`KB_STORAGE=sqlite`，`server/src/index.ts:64`，Docker 数据卷 `ikit-data` 持久化）。
3. 现有 `addCol` 机制（`store.ts:84-102`）已是「按需补列」的自动迁移范式。
4. `node:sqlite`（Node 内置 SQLite）版本支持 `ALTER TABLE ... DROP COLUMN`，但受限制（列被索引/约束/触发器引用时不可 DROP；本表无这些，理论可行）。

### 推荐方案：**A+（保留旧库列 + 新库不建列 + 停止读写）**

代码改动（与 §3.1 `store.ts` 一致）：

- `CREATE TABLE entries` 去掉 5 死列（新库自动干净）；
- 删除 5 行 `addCol` 迁移；
- 删除 `load()` 的 5 行列映射；
- 删除 `persist()` INSERT 的 5 列 + 5 值。

对**已部署旧库**的行为：

- 旧库物理上仍含 5 列，但代码**不再 SELECT / INSERT 它们** → 完全忽略；
- 下次任意写操作触发 `persist()` 全量重写时，因 INSERT 未提供这 5 列，它们自动回落默认值（`rating/summary/history/share_token → NULL`，`likes → 0`），即**死数据随首次保存自然清除**；
- SQLite 允许表存在「未被引用」的多余列，运行无任何异常。

优点：

- **零重建、零拷贝、零备份窗口、零停机**——不触碰已部署库结构；
- 回滚 = 改回代码（列从未物理删除，数据虽已回落 NULL/0，但本就死数据，无损失）；
- 新库自动干净，等价于「C 新库自动迁移」的诉求，且无需额外迁移函数；
- 存储残留成本可忽略（5 列 INTEGER/TEXT，几乎全 NULL）。

### 备选方案 B：重建表 `DROP COLUMN`

步骤：备份 `knowledge.db` → 建临时表（仅保留列）→ `INSERT ... SELECT` 拷贝 → `DROP TABLE entries` → `RENAME`。或用 `ALTER TABLE entries DROP COLUMN xxx`（×5）。

- 优点：物理回收 5 列。
- 缺点/风险：需停机/备份窗口；拷贝-重建中断可能丢数据；`DROP COLUMN` 若遇任何隐含约束/引用即失败；收益仅「回收几列几乎全 NULL 的存储」，**与风险不成比例**。
- **不推荐**。

### 备选方案 C：新库自动迁移逻辑

把 B 的「重建」封装为一次性迁移函数（首次启动检测列存在 → 重建）。比 B 可控，但仍需重建，且与本仓库「全量重写 persist」的现状相比，A+ 已达成等价结果（死数据自然回落），无需自建重建逻辑。

### 推荐结论

**A+**（保留旧库列不动、新库不建列、停读写）。若未来确需物理删列（如审计要求），届时以 C 形态实现，并先备份。

## 5. 兼容性

### 5.1 老 JSON 数据

- `JsonStore.load()`（`store.ts:21-31`）`JSON.parse` 不校验类型、`save()` 全量 `JSON.stringify` 回写 → 老 JSON 里 `rating/likes/summary/history/shareToken` 键会**残留**。
- 结论：**残留无害**（符合「多余键无害，读取忽略即可」）；读取、展示、写入均不受影响。是否加一次性 strip 见 §8 待确认 2（默认：不强制清理）。
- 注意：因 `JsonStore` 不做字段映射，即使删了类型字段，旧键也不会自动消失；这是**预期且可接受**的行为，非缺陷。

### 5.2 已部署 SQLite 库

- 残留 5 列无害；代码停读写后自动忽略；下次 save 死列回落 NULL/0；无需重建/备份窗口。
- 迁移是**幂等且向前兼容**：老库（有列）+ 新库（无列）两种形态，代码都能正常运行（SELECT/INSERT 均只引用保留列）。

### 5.3 第三方插件引用

- **无**：grep 全仓库无第三方/其它插件读取 `KnowledgeEntry` 的这 5 字段。
- `KnowledgeEntry` 不经 `@ikit/core` 转出口（core 仅 re-export `ChatMessage/KnowledgeEntryInput/EntryVisibility/Viewer/VisibilitySyncMode`）；`KnowledgeService` 接口签名不含死字段 → 服务契约不变，第三方通过 `ctx.knowledge` 得到的对象只是少了 5 个可选属性，属向后兼容。
- 唯一需注意：若未来有 TypeScript 第三方包显式访问 `entry.rating` 会编译报错——但仓库内外均无此类引用，风险为零。

## 7. 风险与回滚

| 风险 | 等级 | 说明 | 缓解 / 回滚 |
|---|---|---|---|
| 删字段后遗漏前端/后端消费点导致 tsc/vite 报错 | 中 | 已全量 grep，消费点仅 §3 所列；仍可能漏 | 以「构建通过」为第一验收门；报错即补删 |
| 热门文章排序语义连带变化 | 低 | 删 `score()` 后排序逻辑必须改；默认改为 `updatedAt 降序`（零行为变化） | 见 §8 待确认 1；若选 `views 降序` 则属**有意的行为变更**，需单独确认 |
| SQLite 迁移引发数据风险 | **极低** | A+ 不重建、不删列，仅停读写 | 回滚 = 改回代码（恢复类型字段 + SELECT/INSERT 列 + addCol）；列从未物理删除 |
| 老 JSON 死键残留被误判为「清理不彻底」 | 低 | JSON 多余键无害，属预期 | 文档明示「无害、读取忽略」；可选一次性 strip（§8-2） |
| 版本历史数据丢失 | 低（已确认下线） | `history` 停止写入后，老库中已存在的历史 JSON 数据在下次 SQLite save 时回落 NULL | 该功能已下线且无恢复 UI，数据无保留价值；若需保留可先导出（§8 无此诉求） |
| 文档与代码不同步 | 低 | 落地后才改文档，存在滞后 | §6 第 5 条作为验收门，逐项核对 |

**回滚总纲**：因 A+ 不做物理删列、不动老库结构，**代码回滚即可完全还原**；JSON/SQLite 数据文件无需任何回滚操作。
