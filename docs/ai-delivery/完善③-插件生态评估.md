## 一、现状摘要（关键事实，决定后续一切判断）

### 1.1 商店目录是「纯元数据硬编码」，不含任何可安装物

`STORE_CATALOG`（`service.ts:25-110`）是 7 条 `PluginStoreItem`（stats/notes/calendar/todo/weather/rss/mdclip），每条只有 `name/title/description/version/author/category/screenshots`，**没有 `entry`、`url`、`hash`、`signature`、`source` 等可安装字段**。截图甚至是用 `screenshotDataUrl()` 内联生成的 SVG data URL。

### 1.2 「安装/更新/卸载」只是改注册表，不落盘代码、不下载

- **install**（`service.ts:291-308`）：从 `STORE_CATALOG` 找到条目，仅向 `config.plugins` push 一条 `PluginRecord`，然后 `persist()`。**不写任何目录、不下载任何代码**。
- **update**（`service.ts:320-329`）：仅把 `p.version = item.version; p.title = item.title`。**无真实代码替换**。
- **uninstall**（`service.ts:310-318`）：仅从 `config.plugins` 过滤掉该条目。**不删目录**；并且 **没有调用 `loaderHooks.onUninstall`**（`index.ts:68` 虽接线了 `onUninstall → loader.uninstall`，但 `service.uninstall` 从不触发它）。后果：第三方包目录仍留在磁盘，重启后 `loader.loadAll()` 会再次 `upsertPackage` 把它注册回来——**「卸载第三方包」当前是假卸载**。
- **rate**（`service.ts:247-261`）：评分评论写进 `config.reviews[name]`（即 `data/plugins.json` 注册表存储），**纯本地**，不上云、不做去重/防刷。

### 1.3 商店 7 个插件的「真实实现」其实是内置服务 + 硬编码前端面板

这 7 个商店插件**并不是第三方包**。它们的真实数据由内置插件 `store-data`（`ctx.storeData`）提供（`routes.ts:367-448` 的 `/api/plugins-data/*`），前端面板是 `StorePluginPanel.vue` 里硬编码的 `<template v-if="panel === 'stats'">` 等分支。也就是说：**「安装」统计/便签等插件，只是把名字写进注册表，面板和服务早已内置存在**。

### 1.4 第三方包链路已通，但安全与动态 UI 均为空白

- `loader.ts` 是唯一的「真第三方加载」链路：扫描 `PLUGIN_DIR` 子目录 → 读 `plugin.json` → `sanitizeManifest`（白名单 key：name/title/version/description/panel/entry/permission；name/panel 正则 `^[a-zA-Z0-9_-]{1,64}$`；entry 默认 `index.js`）→ `import(pathToFileURL(entryPath).href)`。
- **无沙箱、无代码校验**：`entry` 模块的 `apply(ctx, config)` 在**完整 Node 主进程上下文**中执行。`permission` 字段被读进 manifest 但**从未被强制**。
- **第三方 UI 无法随包分发**：前端 `App.vue:158` 的 `STORE_PANELS` 与 `StorePluginPanel.vue:8` 的 `TITLE` 都是硬编码常量；`hello` 面板只是 `StorePluginPanel.vue` 里 `v-else` 的兜底文案。第三方插件包只能注册**服务**（`ctx.set('hello', ...)`），却没有任何 API 路由自动暴露它，也没有动态前端渲染入口。
- 示例 `plugins/hello` 只有 `plugin.json`（name/title/version/description/panel/entry）+ `index.ts`（`export default { apply }`），**没有 dependencies 声明、没有 hash、没有作者/分类元数据**。

### 1.5 结论性判断

当前「插件生态」= **注册表（启停/排序/按组可见，真）+ 商店目录（硬编码元数据，假安装）+ 第三方包加载（真加载，但零安全、假卸载、无动态 UI）**。用户想要的「真实第三方市场 / 安全扫描 / 导出导入」需要先把「安装=落盘+校验+可卸载」「目录=可配置远端源」「包=带哈希/依赖的标准化 artifact」这三层地基补起来。

## 二、逐项评估

> 每项给：现状、目标能力、技术路径、工作量（小/中/大）、风险、前置依赖。

### 2.1 插件导出 / 导入

**现状**：无导出/导入能力。第三方包以「目录 = `plugin.json` + `entry` + 资源」形式存在（`plugins/hello`），仅靠人工放目录 + 重启/`loadAll` 加载。

**目标能力**：把已安装（尤其第三方）插件打包为可分发的目录/zip；接收方校验后装入 `PLUGIN_DIR` 并注册，可增量热装。

**技术路径**：
- **导出**：
  - 以包目录为单元，读 `plugin.json`，打包目录内白名单文件（排除 `node_modules/`、`.git/`、`*.log`、`data/` 等）。
  - 两种格式：**目录复制（零依赖，推荐首期）** 与 **zip（需引入打包/解包库，如 `archiver`+`yauzl` 或系统 `tar`/`zip`）**。
  - 导出时顺带写入 `manifest`（含 `sha256`、`author`、`dependencies`、`minIkit`），让包「自描述」。
- **导入**：
  - 接收目录或 zip → 解压到临时目录（隔离，`PLUGIN_DIR/.staging`）→ 校验 → 落位 `PLUGIN_DIR/<name>` → 触发 loader 单包加载 + `upsertPackage`。
  - 校验清单：manifest 白名单字段 + name/panel 正则；`entry` 必须落在包目录内且**无 `../`（防路径穿越/zip-slip）**；解压总量上限（防 zip 炸弹）；同名冲突（已存在则要求升级或拒绝）；`sha256` 匹配（若携带）。
- **loader 需补「单包热加载」**：当前只有全量 `loadAll()`（`loader.ts:71`），需新增 `loadOne(name)` 供导入/更新后即时生效，而非重启。

**工作量**：**中**（导出=小~中；导入=中，主要是校验与增量加载）。

**风险**：
- **导入即代码执行**：`entry` 是任意 Node 代码，导入成功的那一刻起它就有权 `fs/child_process/process` 全量访问（当前无任何边界）。→ 必须在 UI/API 层强制「仅 admin + 二次确认 + 风险提示」，并把「信任边界」写清楚（见第六节）。
- **路径穿越 / zip-slip / 解压炸弹**：文件名 `../`、绝对路径、软链接、超大文件。
- **同名覆盖与版本/依赖一致性**：`plugin.json` 目前无 `dependencies`/`minIkit` 声明，无法约束「依赖某个内置服务（如 llm/storeData）或某个 i-kit 版本」。
- **覆盖已装插件导致服务重复 apply**：loader 用 `applied` 标志防重复（`loader.ts:33-39`），但导入覆盖同名包时需先正确卸载旧实例（含 `dispose`），否则旧服务残留。

**前置依赖**：
1. `plugin.json` manifest 扩展（`author/description/category/dependencies/minIkit/sha256`）。
2. `PluginRecord` 增加 `source/sha256/installedAt/updatedAt` 等字段（见 2.4）。
3. loader 增加 `loadOne`/`reloadOne` 与「真卸载（删目录 + 释放实例）」。
4. 修复 `uninstall` 不触发 `onUninstall` 的缺口。

### 2.2 真实第三方市场

**现状**：`STORE_CATALOG` 硬编码，无远端源、无 hash/signature、无版本清单。

**目标能力**：从远端目录源发现、下载、校验、安装、更新插件；**不强制要求自建服务器**。

**推荐架构（静态 JSON 目录 + 版本清单 + 内容哈希 + 可选签名）**：
- 目录源是一份（或多份）**静态 JSON**，托管在任意 HTTPS 静态托管（GitHub Pages / GitHub Releases / CDN / 对象存储 / 自有服务器）。
- 每条插件带 `versions[]`，每个版本带 `url` + `sha256` +（可选）`signature` + 依赖/版本约束。
- 客户端（`plugin-registry` 服务）拉取 JSON → 与本地注册表比对 → 下载 → 校验 → 落盘 → 注册。

**远端目录格式草案（见第四节）**。

**安装来源校验**：
- `sha256` 内容哈希**必做**（防传输/托管被篡改）；`signature`（ed25519）**可选**（防源头投毒，需密钥管理）；全程 HTTPS；来源域名白名单（默认只信任官方源）。

**更新策略**：
- 拉取 registry JSON → 对每个已装插件取远端最新稳定版本 → 用**语义化版本（semver）比较** → 有更新则下载新版本 zip → 校验 hash → 备份旧目录 → 落盘 → `reloadOne` 热更。失败回滚到备份。
- 版本选择要区分 `pre-release`（如 alpha/beta）与稳定版，避免误装。

**「不依赖自有服务器也可行」的最小方案（推荐）**：
- 用 **GitHub Releases**：每个插件一个 release，`zip` 作为 asset；仓库根放一份 `registry.json`，走 `https://raw.githubusercontent.com/<owner>/<repo>/main/registry.json`（或 jsDelivr `cdn.jsdelivr.net/gh/...`）。
- `url` 直接指向 release asset；发布流程用 GitHub Actions 在打 tag 时自动算 `sha256` 写回 registry.json。
- 签名可在 P2 再加（GitHub Release 的 asset 本身已有 GitHub 身份背书，但对「源头投毒」仍需你自己的信任模型）。

**工作量**：**中**（静态 JSON + 拉取 + semver + hash 校验 + 下载落盘）；若上升到**自建 registry API + 审核流 + 评分云端同步 + 签名密钥轮换**，则**大**。

**风险**：
- **供应链可用性**：依赖 GitHub/CDN 的可用性与被墙风险（国内部署需考虑镜像）。
- **源头投毒**：hash 防「传输篡改」，防不了「上游仓库被攻破后官方主动发布恶意包」——只能靠签名 + 来源信任 + 人工审核。
- **更新兼容性**：版本号不遵循 semver 会导致比较逻辑错乱；需约定 `minIkit` 约束避免装到不兼容版本。
- **缓存与热更**：远端 JSON 需本地缓存 + 可手动刷新，避免每次请求都打远端。

**前置依赖**：
1. 2.1 的「真安装/真卸载/单包热载」全部落地（否则市场装进来也删不掉）。
2. `PluginRecord` 增补 `source/url/sha256` 字段。
3. `plugin.json` 增补 `dependencies/minIkit`。
4. 前端 `PluginStore.vue` 与 `lib/plugins.ts` 支持「从远端目录渲染条目 + 展示来源/哈希/更新可用」，并把 `install` 从「写注册表」升级为「下载+校验+落盘」。

### 2.3 安全扫描

**现状**：`sanitizeManifest` 只校验 manifest 字段格式，`entry` 代码零校验、零沙箱；`permission` 字段读而不执行。

**目标能力**：在安装/加载时做静态检查，降低（**而非消除**）第三方代码风险。

**务实分层（来源可信 > 静态检查 > 沙箱）**：

- **L1 来源可信（必做，性价比最高）**：`sha256` 内容哈希（防篡改）+ 可选 `ed25519` 签名（防投毒）+ HTTPS + 来源域名白名单。这是**投入产出比最高**的一层，先做它。
- **L2 静态检查（安装/加载时，启发式，警告级）**：
  - **入口文件白名单校验**：`entry` 必须落在包目录内、无 `../`、扩展名白名单（`.js/.cjs/.mjs/.ts`）；校验后加载，**拒绝越界**。
  - **依赖声明检查**：`dependencies`/`minIkit` 声明与当前环境比对，不满足则拒绝或强提示。
  - **危险 API 启发式扫描（局限大，仅作提示）**：对 `entry` 及其 import 的源码做正则/词法扫描，标记 `child_process`、`eval(`、`new Function`、`Function(`、`require(`、`process.`、`fs.`、`http(s)://` 等模式。**但 JS 动态执行（间接 eval、动态 import、原型链/构造器逃逸、混淆）使纯静态判定不可靠**——扫不到 ≠ 安全。因此结果定位为「安装前风险提示 + 保留审计日志」，**不做硬阻断**（否则误杀大量正常插件）。
  - **代码评审 + 来源可信 + 哈希为主**：对官方源外的插件，走「人工看一眼 + hash 锁定」。
- **L3 沙箱（Node vm，评估后不建议首期引入）**：
  - `node:vm` **不是安全边界**（Node 官方文档明确警告，逃逸手段多，如经构造器链拿回宿主 `global`、原型污染等），且 i-kit 第三方插件**需要通过 `ctx.set/inject` 与 Cordis 服务深度集成**，vm 隔离会切断这些能力。
  - 真正隔离需 `worker_threads`（有限环境 + 资源限制）或独立进程/容器边界，成本高、且要重写第三方插件与主进程的通信协议（服务调用、事件、配置注入）。
  - **结论**：首期**不引入 vm 沙箱**；以「签名/哈希 + 来源可信 + 静态启发 + 可选人工审核 + 导入即信任的明确提示」为务实方案。仅当未来要运行**完全不可信**代码时，再评估独立 worker/进程边界（P2 可选）。

**工作量**：L1=**小~中**（哈希校验）；L2 静态启发=**中**（白名单校验小、危险 API 扫描中）；L3 沙箱=**大**（且收益有限、风险自引入）。

**风险**：
- **误报/漏报**：静态扫描对动态代码必然漏报，对正常插件可能误报（如插件本就该用 `fs` 读自己的资源）。
- **「安全」错觉**：过度宣传静态扫描会让人误以为可安全运行不可信代码——必须在 UI 与文档写明「扫描是辅助，不构成安全保证」。
- **审计日志膨胀**：每次安装/更新记录扫描结果与哈希，需设计存储。

**前置依赖**：2.1/2.2 的「可下载 artifact + hash 字段 + manifest 扩展」；以及一个「来源/信任策略」的明确决策（见第六节）。

### 2.4 结合现有 STORE_CATALOG / install / update / rate 现状，指出渐进替换与数据模型改动

**（a）能渐进替换（不改外部契约，先做低风险）**：
- **`STORE_CATALOG` 外置化**：从「代码内硬编码数组」改为「配置文件/远端 JSON 目录源」，保留当前 7 条作为 `seed` 默认值，`store()`/`categories()`/`install`/`update` 改为读目录源。这是市场能力的前置，且可完全向后兼容。
- **`install`/`update` 从「改字段」升级为「真安装」**：下载（或导入）→ 校验 → 落盘 → `loadOne/reloadOne`。对外仍可复用 `/api/plugin-store/install`、`/:name/update` 路由签名，只是内部实现替换。
- **`rate` 保持本地**：短期继续存 `config.reviews`，仅补「去重（每人每插件限一条）/ 编辑」即可，不必急着上云。

**（b）必须改数据模型（`PluginRecord` 字段不够）**：
现有 `PluginRecord`（`types.ts:4-21`）只有 `name/title/version/enabled/builtin/order/visibleGroups/panel`，**缺来源、哈希、依赖、作者、时间戳**。建议**新增（全部可选，向后兼容，缺省走默认）**：

| 字段 | 用途 | 说明 |
|---|---|---|
| `source` | `'builtin'\|'catalog'\|'market'\|'local'` | 区分内置/商店内置/远端市场/本地导入 |
| `packageUrl` | 市场安装的下载地址 | 更新时复用 |
| `sha256` | 内容哈希 | 校验 + 更新比对 |
| `signature?` | ed25519 签名（可选） | P2 |
| `dependencies?` | 依赖声明（服务名 / i-kit 版本） | 一致性校验 |
| `minIkit?` | 最低 i-kit 版本约束 | 一致性校验 |
| `author?/description?/category?` | 元数据 | 目前只在 `PluginStoreItem`，`PluginRecord` 无 |
| `installedAt?/updatedAt?` | 时间戳 | 审计/展示 |

- **迁移策略**：`ensureLoaded` 已有多轮迁移范式（`service.ts:120-148`），新增字段用「缺省补默认」即可，JSON/SQLite 兼容；`PluginRecord` 是 JSON 持久化，加可选字段**不破坏旧数据**。
- **结构统一**：目前 `STORE_CATALOG`（`PluginStoreItem`）与注册表（`PluginRecord`）两套结构靠 `name` 硬关联，字段重复且易漂移。建议统一为「**目录条目（含全部元数据 + 安装物地址/哈希）+ 安装后注入运行时字段（enabled/order/visibleGroups/installedVersion）**」。
- **reviews 存储位置**：现与 `plugins` 同存 `plugins.json`；若未来做云端评分，需把「本地评论」与「远端评分」分离（本地 `reviews` 保留，远端另存缓存）。

## 三、推荐架构草案

### 3.1 总体：三层解耦

```
[远端目录源(静态 JSON/Registry API)]  ← 可选多源
        │ 拉取/校验(hash/sig)
        ▼
[插件注册表 PluginRegistry]  ──启用/排序/可见性/评分──▶  plugins.json
        │ 安装=下载+校验+落盘  卸载=删目录+释放  更新=semver+回滚
        ▼
[插件包加载器 Loader]  ──scan/loadOne/activate/deactivate/uninstall──▶  PLUGIN_DIR/<name>/
        │ 动态 import 入口
        ▼
[Cordis ctx]  ──ctx.set 服务──▶  内置服务(llm/knowledge/agent/storeData/account…)
```

### 3.2 远端目录 JSON 示例字段（推荐草案）

```jsonc
// registry.json —— 静态目录源（GitHub Releases / 静态托管 / 自有服务器）
{
  "schema": 1,                       // 目录格式版本，便于演进
  "name": "i-kit 官方插件市场",
  "updatedAt": "2026-09-04T10:00:00Z",
  "plugins": [
    {
      "name": "hello",               // 唯一标识，^[a-zA-Z0-9_-]{1,64}$
      "title": "Hello 示例插件",
      "description": "第三方插件包示例…",
      "author": "i-kit 官方",
      "category": "工具",
      "homepage": "https://example.com/hello",   // 可选
      "minIkit": "0.1.0",            // 最低 i-kit 版本（semver）
      "versions": [
        {
          "version": "1.1.0",        // semver，稳定版
          "url": "https://…/hello-1.1.0.zip",
          "sha256": "hex…",          // 必做：内容哈希（zip 包整体）
          "signature": "base64…",    // 可选：对 sha256 的 ed25519 签名（P2）
          "dependencies": {          // 可选：依赖的内置服务/其他插件
            "storeData": "^1.0.0"
          },
          "size": 12345,             // 可选：解压前大小，防炸弹提示
          "publishedAt": "2026-09-04T09:00:00Z",
          "changelog": "…"           // 可选
        }
      ]
    }
  ]
}
```

- **包内 `plugin.json`（artifact 内，标准化后）**：在现有 `name/title/version/description/panel/entry/permission` 基础上，**增补** `author`、`category`、`dependencies`、`minIkit`、`sha256`（可选，导出时写入）。
- **签名语义**：`signature = sign(sha256(artifact))`，用 ed25519 公钥（`publicKey` 随目录源分发或硬编码于客户端）验签。哈希防篡改、签名防投毒。

### 3.3 最小可行（不依赖自有服务器）

- 仓库 `ikit-plugins`：根放 `registry.json`；每个插件一个 GitHub Release，`zip` 为 asset。
- `url` 指向 release asset；发布用 GitHub Actions 自动算 `sha256` 回写 registry.json。
- 客户端默认只信任官方源 URL（环境变量 `PLUGIN_REGISTRY_URL`，可覆盖；`PLUGIN_REGISTRY_ALLOWED_HOSTS` 白名单）。
- 签名后置（P2）——最小方案先靠「官方仓库 + 哈希 + HTTPS」兜底。

## 四、安全分层（落地顺序与边界）

```
L0 边界约束：安装/导入/更新 仅 admin，二次确认 + 风险提示（UI+API 双重）
L1 来源可信：HTTPS + 来源域名白名单 + sha256 哈希（必做）
L2 静态检查：manifest 白名单/入口路径校验 + dependencies/minIkit 校验 + 危险 API 启发扫描（警告级，非阻断）
L3 可选沙箱：worker/进程/容器边界（仅运行完全不可信代码时；Node vm 不构成安全边界，首期不引入）
```

- **判断原则**：能上 L1 就上 L1（性价比最高）；L2 是「提示 + 审计」而非「安全保证」；L3 是最后手段且要重写第三方插件与主进程的集成协议。
- **UI 措辞**：安装第三方/市场插件时明确标注「该插件将获得与主程序同等的系统权限，仅安装你信任的来源」；对「非官方源」给醒目警告色。

## 五、分阶段路线图（P0 / P1 / P2）

### P0 — 地基（不改对外行为、低风险、先做）

**范围**：
1. **修复卸载语义**：`service.uninstall` 调用 `onUninstall`，`loader.uninstall` 真正「释放实例 + 删除 `PLUGIN_DIR/<name>` 目录 + 从内存 Map 移除」；`uninstall` 与「仅禁用」分离。这是最优先项（当前第三方包卸不掉、重启复活）。
2. **`PluginRecord` 数据模型扩展**（`source/sha256/packageUrl/dependencies/minIkit/author/description/category/installedAt/updatedAt`，全可选 + 迁移兼容）。
3. **`STORE_CATALOG` 外置化**：移出代码为默认目录源（`data/plugin-catalog.json` 或内置 seed），`store()/categories()/install/update` 改为读目录源；保留 7 条默认，行为不变。
4. **`plugin.json` manifest 扩展 + `sanitizeManifest` 强化**（入口路径越界校验、扩展名白名单、字段补全）。
5. **loader 增加 `loadOne/reloadOne`**，为导入/更新打底。

**依赖**：无外部依赖；纯内部重构。
**验收**：第三方包卸载后目录删除、重启不再复活；旧 `plugins.json` 数据加载兼容；`store()` 输出与改造前一致；越界 `entry` 被拒。
**建议先做**：**第 1 项（修复卸载）**——它暴露了现有 bug，且是导出/导入与市场共用的地基，风险最低、收益立现。

### P1 — 核心能力（导出/导入 + 静态市场 + 安全 L1/L2）

**范围**：
1. **导出/导入**（目录 + zip；校验：路径穿越/解压炸弹/manifest 白名单/hash；单包热装）。
2. **静态市场接入**：远端 registry.json 拉取 + semver 更新比对 + `sha256` 校验 + 下载落盘 + 失败回滚；前端 `PluginStore.vue` 展示来源/版本/更新可用，`install/update` 真下载。
3. **安全 L1+L2**：哈希必做、来源白名单、静态启发扫描（警告级 + 审计日志）、导入/安装「仅 admin + 二次确认 + 风险提示」。

**依赖**：P0 全部；引入 zip 打包/解包库（或先做目录版）；`PLUGIN_REGISTRY_URL`/`PLUGIN_REGISTRY_ALLOWED_HOSTS` 环境变量。
**验收**：第三方包可导出→另一实例导入→生效；从静态市场安装/更新真实落盘并热更；篡改 artifact 被 hash 拒绝；越界/超大包被拒；卸载彻底。
**建议先做**：**导出/导入（目录版）**，它不依赖远端、闭环最完整，能立刻验证「真安装/真卸载/单包热载」整条链路。

### P2 — 生态成熟（需用户决策，可并行或后置）

**范围**：
1. **签名校验（ed25519）+ 密钥管理 + 来源信任列表**。
2. **自建 registry API / 审核流 / 评分评论云端同步**（可选，仅当要运营自有市场）。
3. **可选沙箱**（独立 worker/进程边界，仅运行完全不可信代码时评估）。
4. **拖拽排序实时预览**（总览第六节第 3 项里另一子项，可独立排期）。

**依赖**：P1；用户对「是否运营自有市场 / 信任模型 / 密钥管理」的决策。
**验收**：签名错误拒绝安装；官方源外插件走人工审核；密钥轮换/吊销可用。
**建议先做**：**拖拽排序实时预览**（独立小项，与市场/签名无关，可随手落地），签名与自建市场等用户决策后再排。

## 六、待用户决策问题（含推荐默认）

| # | 问题 | 推荐默认 | 影响 |
|---|---|---|---|
| D1 | **是否运营自有市场？**（自建 registry API + 审核 + 云端评分）还是先用 GitHub Releases/静态 JSON 托管？ | **否**：先用静态 JSON + GitHub Releases 最小方案，自建市场后置到 P2 | 决定 P1 的目录源形态与 P2 是否立项 |
| D2 | **信任模型**：hash-only（防篡改）还是 hash+签名（防投毒）？ | **首期 hash-only + HTTPS + 官方源白名单**；签名后置 P2 | 决定是否引入密钥体系与验签链路 |
| D3 | **签名密钥管理**（若 D2 选签名）：私钥谁保管、如何轮换/吊销、公钥如何分发？ | **暂缓**，P2 再定；默认「官方私钥不出 CI，公钥随目录源分发」 | 影响 P2 实现与运维流程 |
| D4 | **卸载语义**：卸载第三方包时是否**删除** `PLUGIN_DIR` 下目录？ | **删除目录（物理卸载）**；「仅禁用」保留为另一独立操作 | 决定 P0 第 1 项的实现与「卸载」二字含义 |
| D5 | **导入/安装信任边界**：是否仅 admin + 强制二次确认 + 风险提示？ | **是**：仅 admin，且非官方源给醒目警告 | 决定 API/UI 的鉴权与交互 |
| D6 | **评分评论是否上云**（远端市场）？ | **保持本地**，云端评分放 P2 | 决定 `reviews` 数据模型是否分离 |
| D7 | **第三方 UI 分发范围**：是否允许插件自带前端面板（需引入动态组件加载机制，安全面扩大）？ | **首期不放开**：第三方插件仅提供后端服务 + 由主程序白名单渲染面板（沿用现状）；动态前端随包分发后置评估 | 决定前端架构改动量（影响很大） |

> 说明：D7 是最影响架构的一项——当前第三方插件 UI 是「主程序硬编码面板 + 内置 store-data 服务」模式，若要「第三方自带 UI」，需引入前端动态组件/沙箱加载，安全与构建复杂度显著上升，建议**默认不放开**，先只做「后端服务型第三方插件」生态。

## 七、风险汇总

| 类别 | 风险 | 等级 | 缓解 |
|---|---|---|---|
| **供应链** | 依赖 GitHub/CDN 可用性与被墙风险；上游仓库被攻破后官方发布恶意包 | 高 | 本地缓存目录源 + 官方源白名单 + hash 锁定；签名（P2） |
| **远程代码执行** | 第三方 `entry` 是任意 Node 代码，导入/安装即 RCE；静态扫描无法根除 | **高** | 来源可信（hash/sig）+ 仅 admin + 二次确认 + 审计 + 可选运行边界（P2） |
| **维护成本** | 自建市场/签名/审核流的人力与运维；包格式向后兼容；loader 与 Cordis 生命周期边界 | 中 | 分层渐进（P0→P1→P2）；manifest `schema` 版本化；先做静态 JSON 不自建服务 |
| **卸载/热更正确性** | `dispose` 未正确清理导致旧服务残留；覆盖安装重复 `apply`；卸载不删目录（现状 bug） | 中 | P0 修复 + `reloadOne` 先释放旧实例再加载新实例 + 回滚备份 |
| **数据兼容** | `PluginRecord` 增字段、`reviews` 上云导致 JSON/SQLite 迁移 | 低~中 | 新增字段全可选 + 复用 `ensureLoaded` 迁移范式 + 版本化 |
| **安全错觉** | 过度宣传静态扫描/沙箱让人误以为可运行不可信代码 | 中 | UI/文档明示「扫描是辅助，不构成安全保证」，信任边界写清楚 |

---

## 八、一句话结论

先把「**安装/卸载/加载**」从「改注册表字段」升级为「落盘 + 校验 + 可彻底卸载 + 单包热载」（P0），再在同一地基上做「**导出/导入 + 静态 JSON 市场 + 哈希校验**」（P1），最后按用户决策上「**签名 / 自建市场 / 可选沙箱**」（P2）；安全以**来源可信（哈希/签名）为主、静态检查为辅、沙箱非必需**，并以「仅 admin + 二次确认 + 信任边界明示」兜底。
